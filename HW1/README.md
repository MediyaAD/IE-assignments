## سؤال ۱: merge و rebase

**هرکدام از این دستورها چه کاری انجام می دهند؟** هر دو دستور تغییرات یک branch را وارد branch دیگر می‌کنند، اما روش آن‌ها فرق دارد.
**تفاوت در نحوۀ ترکیب تغییرات:**
- `git merge` دو شاخه را با یک **کامیت ادغام (merge commit)** که دو والد دارد به هم وصل می‌کند. کامیت‌های قبلی همان‌طور که بودند می‌مانند و هیچ کامیتی تغییر نمی‌کند.
- `git rebase` کامیت‌های branch فعلی را برمی‌دارد و یکی‌یکی **روی هد branch مقصد دوباره اجرا می‌کند (replay)**. نتیجه چند کامیت جدید است که محتوایشان همان است ولی شناسۀ (hash) تازه دارند و کامیت‌های قدیمی دیگر از branch قابل دسترسی نیستند.

**تفاوت در شکل تاریخچه:** merge تاریخچه را به‌صورت گرافی با انشعاب و پیوند نگه می‌دارد. rebase تاریخچه را **خطی** می‌کند، گویی کار از ابتدا روی آخرین نسخۀ مقصد شروع شده بود. بنابراین rebase تاریخچه را بازنویسی می‌کند و merge نمی‌کند.

**موقعیت مناسب merge:** ادغام شاخۀ `feature` در `main` که branch مشترک تیم است و بقیه آن را دریافت کرده‌اند:

```bash
git switch main
git merge feature
```

دلیل انتخاب: merge هیچ کامیتی را بازنویسی نمی‌کند، پس برای هم‌تیمی‌ها مشکلی پیش نمی‌آورد. merge commit زمان و محل پیوستن feature را در تاریخچه نشان می‌دهد.

**موقعیت مناسب rebase:** branch شخصی و push‌نشدۀ `feature` از `main` عقب مانده و می‌خواهیم پیش از ایجاد pull request آن را به‌روز کنیم:

```bash
git switch feature
git fetch origin
git rebase origin/main
```

دلیل انتخاب:چون فقط خود شخص از این branch استفاده می‌کند، پس بازنویسی تاریخچه آسیبی به کسی نمی‌زند. نتیجه تاریخچه‌ای خطی و تمیز است که بررسی آن آسان است. در واقع به طور کلی کامیت‌هایی که push شده و دیگران دریافت کرده‌اند را rebase نمی‌کنیم.

## سؤال ۲: انتخاب بخشی از تغییرات

**هانک چیست؟** در خروجی `git diff`، تغییرات هر فایل به چند بلوک پیوسته تقسیم می‌شود. هر بلوک را یک hunk می‌گویند. هر hunk با سرتیتری مثل `@@ -10,6 +10,8 @@` شروع می‌شود که شمارۀ خط‌های آغاز و طول بخش را در نسخۀ قدیم و جدید نشان می‌دهد. پس از آن خط‌های بدون تغییر اطراف و خط‌های حذف‌شده (`-`) و اضافه‌شده (`+`) می‌آیند.

**بررسی تعاملی و staging بخشی از تغییرات:**

```bash
git add -p app.py        # یا: git add --patch app.py
```
هر hunk توسط Git نشان داده می شود و می‌پرسد چه کنم. گزینه‌های مهم:

- `y`: این hunk را وارد staging کن.
- `n`: این hunk را فعلاً نگذار.
- `s`: hunk را به بخش‌های کوچک‌تر تقسیم کن (split). این گزینه فقط وقتی کار می‌کند که بین خط‌های تغییریافته خط بدون تغییر باشد.
- `e`: hunk را دستی ویرایش کن. برای جدا کردن تغییرات خط‌ به‌ خط مفید است.
- `a` / `d`: همۀ hunkهای باقی‌ماندۀ فایل را بگذار / نگذار.
- `q`: خارج شو. hunkهای قبلاً انتخاب‌شده در staging می‌مانند.
- `?`: راهنما.

پس از انتخاب، نتیجه را بررسی و کامیت می‌کنیم:

```bash
git diff --staged        # آنچه کامیت می‌شود
git diff                 # آنچه هنوز در staging نیست
git commit -m "Fix bug"
```

(برای فایل جدید untracked، ابتدا `git add -N file` لازم است تا `-p` آن را ببیند.)

**فایده.** اغلب در یک فایل چند کار نامرتبط انجام می‌دهیم، مثلاً رفع یک باگ و تغییر ظاهر کد. با `git add -p` هر کار در کامیت جداگانۀ خودش ثبت می‌شود. این کامیت‌ها منسجم و کوچک‌اند و کارهای زیر را آسان می‌کنند: بازبینی کد، `git revert` یک تغییر مشخص، `git bisect` و فهمیدن علت هر تغییر از روی تاریخچه.

## سؤال ۳: یافتن منشأ خطا با git bisect

**روش کار.** `git bisect` با **جست‌وجوی دودویی** در تاریخچه، اولین کامیتی را پیدا می‌کند که خطا را وارد کرده است. اگر بین کامیت سالم و معیوب n کامیت باشد، فقط حدود log₂(n) مرحله لازم است.

**مراحل:**

1. شروع جست‌وجو:
   ```bash
   git bisect start
   ```
2. مشخص کردن کامیت معیوب (معمولاً کامیت فعلی) و یک کامیت سالم شناخته‌شده (مثلاً یک tag قدیمی):
   ```bash
   git bisect bad HEAD
   git bisect good v1.0       # یا شناسۀ کامیت، مثلاً a1b2c3d
   ```
3. Git کامیتی را در **وسط** این بازه checkout می‌کند. برنامه را اجرا یا تست می‌کنم و نتیجه را اعلام می‌کنم:
   ```bash
   git bisect good     # اگر خطا وجود ندارد
   git bisect bad      # اگر خطا وجود دارد
   git bisect skip     # اگر کامیت قابل تست نیست، مثلاً build نمی‌شود
   ```
4. Git بازه را نصف می‌کند و مرحلۀ قبل تکرار می‌شود تا پیام `<hash> is the first bad commit` ظاهر شود.
5. پایان و برگشت به شاخۀ اصلی:
   ```bash
   git bisect reset
   ```

**خودکارسازی.** اگر اسکریپتی داشته باشیم که با کد خروج ۰ سالم و با کد خروج ۱ تا ۱۲۷ (به‌جز ۱۲۵) معیوب را نشان دهد، کل فرایند خودکار می‌شود:

```bash
git bisect start HEAD v1.0
git bisect run ./test.sh
```

**مثال.** تست `test_login` در نسخۀ `v1.0` پاس می‌شد ولی امروز رد می‌شود و بین این دو نسخه ۲۰۰ کامیت وجود دارد. با bisect حدود ۸ بار تست کافی است. دلیل: ۲^۸ = ۲۵۶ ≥ ۲۰۰.

**چرا مفید است؟** بررسی دستی ۲۰۰ کامیت زمان‌بر است. bisect به‌جای حدس زدن، به‌صورت سیستماتیک و با تعداد مرحلۀ کم، دقیقاً کامیتی را نشان می‌دهد که باگ را ساخته است. سپس می‌توان تغییرات همان کامیت و نویسنده و پیام آن را بررسی کرد. این روش وقتی بهتر کار می‌کند که کامیت‌ها کوچک و منسجم باشند (سؤال ۲).

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۱) دستورهای بررسی

```bash
git status               # نمای کلی: staged، unstaged و untracked
git diff                 # تغییرات هنوز واردنشده به staging (working tree در برابر index)
git diff --staged        # تغییرات آمادۀ کامیت (index در برابر آخرین کامیت)؛ معادل: git diff --cached
```

در `git status` فایل `README.md` همزمان در دو بخش دیده می‌شود: «Changes to be committed» و «Changes not staged for commit».

**تفاوت دو دسته.** تغییرات staged نسخه‌ای از فایل‌اند که در لحظۀ اجرای `git add` در index ذخیره شده است. ویرایش‌های بعدی فقط در working tree هستند و به index منتقل نشده‌اند، پس unstaged به حساب می‌آیند. نتیجه: فایل در این لحظه سه نسخۀ مختلف دارد (آخرین کامیت، index و working tree).

### ۲) کامیت معمولی بدون `-a`

```bash
git commit -m "Update README"
```

فقط **تغییرات staged** یعنی همان بخشی که قبلاً add کرده بودم کامیت می‌شود. ویرایش‌های بعدی در working tree می‌مانند و پس از کامیت همچنان در `git status` به‌صورت «Changes not staged for commit» دیده می‌شوند.

دلیل: کامیت از **محتوای index** ساخته می‌شود، نه از محتوای working tree. گزینۀ `-a` است که پیش از کامیت همۀ تغییرات فایل‌های tracked را هم stage می‌کند.

### ۳) نادیده گرفتن پوشۀ `/tmp`

در فایل `.gitignore` در ریشۀ مخزن این خط را می‌نویسم:

```
/tmp/
```

(اسلش ابتدایی یعنی فقط پوشۀ `tmp` در ریشۀ مخزن؛ اسلش انتهایی یعنی این الگو فقط یک پوشه را نشان می‌دهد.) سپس خود `.gitignore` را کامیت می‌کنم تا برای همۀ اعضای تیم اعمال شود. برای درستی‌سنجی از `git check-ignore -v tmp/x.txt` استفاده می‌کنم. برای قواعد شخصی که نباید وارد مخزن شود، فایل `.git/info/exclude` هم هست.

**آیا برای فایل tracked کافی است؟** خیر. `.gitignore` فقط روی فایل‌های **untracked** اثر دارد. فایلی که قبلاً کامیت شده، ignore نمی‌شود و تغییراتش همچنان رصد می‌شود. برای خارج کردن آن از tracking، بدون حذف از دیسک:

```bash
git rm --cached path/to/file
git commit -m "Stop tracking file"
```

سپس الگوی آن را به `.gitignore` اضافه می‌کنم. در این سؤال `/tmp` فقط فایل‌های untracked دارد، پس همان `.gitignore` کافی است.

## سؤال ۵: رفع conflict در merge

### ۱) چرا conflict رخ داد؟

گیت یک **merge سه‌طرفه** انجام می‌دهد: کامیت مشترک (جد مشترک)، نوک `main` و نوک `description-feature` را مقایسه می‌کند. هر دو نفر **همان خط** را از نسخۀ مشترک به دو متن متفاوت تغییر داده‌اند و Git نمی‌تواند تشخیص دهد کدام درست است، پس آن را به انسان واگذار می‌کند.

**خیر، هر تغییری باعث conflict نمی‌شود.** اگر دو نفر در یک فایل **خط‌های متفاوت** را تغییر دهند، یا فقط یک طرف خطی را تغییر داده باشد، یا هر دو دقیقاً همان تغییر را داده باشند، Git خودکار و بدون conflict ادغام می‌کند. conflict فقط وقتی پیش می‌آید که دو تغییر در یک ناحیه همپوشانی داشته و با هم ناسازگار باشند.

### ۲) شناسایی فایل‌ها و نقش markerها

```bash
git status                                  # بخش Unmerged paths: both modified: README.md
git diff --name-only --diff-filter=U        # فهرست فقط فایل‌های دارای conflict
git diff                                    # نمایش ناحیه‌های conflict
```

گیت در فایل، دو نسخه را با markerها مشخص می‌کند:

``` <<<<<<< HEAD
متن شاخۀ فعلی (main، تغییر هم‌تیمی)
=======
متن شاخۀ ادغام‌شونده (description-feature، تغییر من)
>>>>>>> description-feature ```

- `<<<<<<< HEAD` تا `=======`: نسخۀ شاخه‌ای که روی آن هستم (`main`).
- `=======` تا `>>>>>>> description-feature`: نسخۀ شاخۀ ادغام‌شونده.

این markerها فقط راهنمای Git برای ویرایش‌اند و نباید در نسخۀ نهایی بمانند.

### ۳) رفع conflict با حفظ هر دو تغییر

1. (اگر هنوز روی `main` نیستم) `git switch main` و سپس `git merge description-feature` که conflict را گزارش می‌دهد.
2. فایل `README.md` را باز می‌کنم، متن هر دو نسخه را به یک متن منسجم تبدیل می‌کنم و سه خط marker را کاملاً حذف می‌کنم.
3. بررسی باقی‌نماندن markerها:
   ```bash
   grep -nE '^(<<<<<<<|=======|>>>>>>>)' README.md    # نباید خروجی داشته باشد
   git diff --check                                    # در صورت وجود marker هشدار می‌دهد
   ```
4. اعلام حل شدن conflict به Git:
   ```bash
   git add README.md
   git status          # دیگر Unmerged paths نباید وجود داشته باشد
   ```
5. تکمیل merge:
   ```bash
   git commit          # یا: git merge --continue
   ```
   پیام پیش‌فرض merge را می‌توانم نگه دارم یا کامل‌تر کنم.
6. بررسی نهایی: `git log --oneline --graph` که کامیت ادغام با دو والد را نشان می‌دهد.

### ۴) لغو merge در حال انجام

```bash
git merge --abort
```

چون پیش از merge، working tree در وضعیت clean بود (تغییر ثبت‌نشده‌ای نداشتم)، این دستور همه‌چیز را دقیقاً به حالت پیش از merge برمی‌گرداند. هیچ کامیتی ساخته نشده و markerها از فایل‌ها حذف می‌شوند.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱) دور ریختن تغییرات یک فایل tracked

```bash
git restore notes.txt
```

(در نسخه‌های قدیمی‌تر Git: `git checkout -- notes.txt`.)

این دستور محتوای `notes.txt` در working tree را از **index** (که با آخرین کامیت یکسان است) بازمی‌گرداند. فقط همین فایل تغییر می‌کند و فایل‌های دیگر دست‌نخورده می‌مانند. index و تاریخچه تغییری نمی‌کنند. **هشدار:** این تغییرات هرگز کامیت یا stage نشده‌اند، پس بعد از این دستور قابل بازیابی نیستند.

### ۲) خارج کردن فایل از staging با حفظ ویرایش‌ها

```bash
git restore --staged notes.txt
```

(معادل قدیمی: `git reset HEAD notes.txt`.)

نسخۀ فایل در **index** به آخرین کامیت برمی‌گردد، یعنی فایل از staging خارج می‌شود. **working tree تغییر نمی‌کند** و ویرایش‌های من حفظ می‌مانند و در `git status` به‌صورت unstaged دیده می‌شوند. تاریخچه هم دست‌نخورده است.

### ۳) بازگرداندن اثر کامیت push‌شده روی `main`

```bash
git revert <hash>      # شناسۀ فرضی: a1b2c3d
git push origin main
```

یک **کامیت جدید** توسط `git revert` ساخته می شود که تغییرات کامیت اشتباه را معکوس می‌کند. اثر آن: working tree و index به حالت پس از بازگردانی تغییر می‌کنند، یک کامیت جدید به انتهای تاریخچه اضافه می‌شود، و کامیت اشتباه و تاریخچۀ قبلی **سالم می‌مانند**. چون این کامیت معمولی است و merge نیست، گزینۀ `-m` لازم نیست.

**چرا حذف کامیت (مثلاً `git reset --hard HEAD~1`) و `git push --force` مناسب نیست؟**

- `main` یک branch مشترک است و هم‌تیمی‌ها کامیت اشتباه را دریافت کرده‌اند. حذف آن از تاریخچه و force push باعث می‌شود تاریخچۀ محلی آن‌ها با سرور **واگرا (diverge)** شود.
- هم‌تیمی‌ها باید تاریخچه را دستی اصلاح کنند. در غیر این صورت با pull بعدی همان کامیت اشتباه دوباره وارد branch می‌شود، یا conflictهای پیچیده پیش می‌آید.
- force push ممکن است کامیت‌هایی را که دیگران در این فاصله روی `main` push کرده‌اند **نابود کند**.
- `git revert` تاریخچه را بازنویسی نمی‌کند، پس push آن عادی و امن است و ردی از اتفاق باقی می‌ماند.
